# Requirements — 91 Degree RKDS

Restaurant Kitchen Display System for **91 Degree BBQ | Fast Food | Chinese**.
Each requirement has a stable ID. Tests, reports, and change requests should reference these IDs.

Related: [ARCHITECTURE.md](ARCHITECTURE.md) · [API_CONTRACTS.md](API_CONTRACTS.md) · [TESTING.md](TESTING.md) (traceability)

---

## 1. Product summary

The owner receives orders through WhatsApp, Foodpanda, phone calls and other channels. They copy the full order text (or type it) into the **owner panel** (`/owner`). The server saves it to PostgreSQL, assigns a daily order number, and starts a deadline timer. The order then appears on the **kitchen display** (`/kitchen`) in real time. The owner later marks it completed or cancelled. Every order stays in the history.

This product is **not a POS**.

## 3. Actors and roles

| Role | How authenticated | Can do |
|---|---|---|
| `OWNER` | Username + password login (created via server CLI) | Create orders, view active/history, complete, cancel, pair/revoke kitchen screens, view kitchen display |
| `KITCHEN` | Device paired using a one-time pairing code generated by an owner | View active orders on `/kitchen` (read-only) |
| Anonymous | — | Owner login page, kitchen pairing page, health endpoints only |

## 4. Functional requirements

### 4.1 Owner panel (`/owner`)

| ID | Requirement |
|---|---|
| FR-OWN-01 | Brand header with restaurant name, current date/time (Asia/Karachi), connection status, logout |
| FR-OWN-02 | Large multi-line textarea for the full order text; supports Ctrl+V/manual paste and typing |
| FR-OWN-03 | Source selector: WhatsApp, Foodpanda, Phone, Other (last choice remembered on the device; default WhatsApp) |
| FR-OWN-04 | Preparation target selector: 15, 20 (default), 25 or 30 min (owner decision Q-08) |
| FR-OWN-05 | Paste-then-review flow (owner decision Q-02). A secondary **Paste** button fills the textarea from the clipboard and sends nothing. The owner reads or edits the text, then presses the primary **Send to Kitchen** button (disabled while the textarea is empty). Ctrl/Cmd+Enter also sends. If the textarea already has text, Paste replaces it and shows an **Undo** toast for 5 s |
| FR-OWN-06 | The Paste button reads the clipboard only after an explicit click. If clipboard access is denied or unavailable (for example in some mobile browsers), focus the textarea and show "Press Ctrl+V (or long-press → Paste) to paste". Never read the clipboard in the background, and never send as a side effect of pasting |
| FR-OWN-07 | Empty or whitespace-only orders are rejected on the client and the server |
| FR-OWN-08 | Visible states: idle → sending → saved (shows assigned order number) / failed (shows reason + Retry). The textarea clears only after the server confirms the order was saved |
| FR-OWN-09 | Double submission is impossible: the button is disabled while sending, and every draft carries an idempotency key |
| FR-OWN-10 | Active orders list with number, source, timer, a text preview, and Complete / Cancel actions |
| FR-OWN-11 | Active-order count in the header |
| FR-OWN-12 | Recent orders (current business day, all statuses) and paged history filtered by business date and status |
| FR-OWN-13 | Search by order number within a selected business date (default: today's business date) |
| FR-OWN-14 | Complete needs a two-step inline confirm ("Tap again to confirm", 3 s window). Cancel needs a confirmation dialog |
| FR-OWN-15 | Kitchen screen management: generate a one-time pairing code, list paired screens, revoke a screen |
| FR-OWN-16 | Unsent draft text, source, prep target and idempotency key survive a page refresh on the same device. They are cleared after a confirmed save and on logout |

### 4.2 Kitchen display (`/kitchen`)

| ID | Requirement |
|---|---|
| FR-KIT-01 | Full-screen, landscape-first layout: brand, connection status, active-order count, clock, sound toggle, full-screen toggle |
| FR-KIT-02 | Order cards sorted oldest active first (by `createdAt` ascending) |
| FR-KIT-03 | Each card shows a large order number, the **complete** original text with line breaks, a prominent timer, and a small source badge. Text is never truncated |
| FR-KIT-04 | 5–10 cards fit comfortably on a 1920×1080 display. If more are active, the board scrolls vertically and shows a "N more below" indicator |
| FR-KIT-05 | New cards animate in and get a "NEW" highlight for 8 s. Completed/cancelled cards animate out. Reduced-motion preference is respected |
| FR-KIT-06 | New-order alert (ADR-028): a clearly audible ~3.5 s sound, once per new order (duplicates ignored; never for snapshot loads or reconnects). Enabled by an explicit staff tap (browser autoplay rules), with a "Tap to enable sound" banner after reload when needed. Per-screen settings: on/off, volume 10–100 %, Test sound, and an indicator that shows whether sound is really audible |
| FR-KIT-07 | No owner controls, forms, pricing or management UI. The view is read-only |
| FR-KIT-08 | An unpaired device sees a pairing screen to enter the owner-issued code |
| FR-KIT-09 | Keeps the screen awake (Screen Wake Lock API) where supported, and degrades silently where not |
| FR-KIT-10 | Cards from a previous business day that are still active show the date (e.g. "Yesterday") so duplicate daily numbers cannot be confused |
| FR-KIT-11 | Mouse cursor auto-hides after 3 s without movement |
| FR-KIT-12 | Per-device density setting (Standard / Large text), remembered on the device |
| FR-KIT-13 | Menu orders show one line per item: large quantity, name and size (ADR-027). No prices on the kitchen screen |
| FR-KIT-14 | Kitchen notes appear in a separate gold "KITCHEN NOTES" block inside the card, line breaks kept, hidden when empty |

### 4.2a Menu ordering and kitchen notes (ADR-027)

| ID | Requirement |
|---|---|
| FR-MENU-01 | The owner switches between **Menu** and **Paste / Type** without losing unsent input in either; the last mode is remembered on the device |
| FR-MENU-02 | Menu mode: category tabs (with selected counts), search, item cards with every size and its menu price, and − / quantity / + per size. − is disabled at 0 and + at 99 |
| FR-MENU-03 | A summary lists every selected line with + / −, a remove button and a reference total from menu prices ("not a bill") |
| FR-MENU-04 | Send creates the order through the same pipeline as text orders (numbering, idempotency, timers, events). The selection and notes clear only after the server confirms |
| FR-MENU-05 | The server resolves item ids against the menu and builds the kitchen text. Unknown or inactive lines → `409 MENU_ITEM_UNAVAILABLE`; the menu reloads and stale lines are flagged, never dropped |
| FR-MENU-06 | The menu is the printed 91 Degree menu ([MENU.md](MENU.md)). Unclear entries are listed for owner verification, not guessed |
| FR-NOTE-01 | Optional "Kitchen Notes / Special Instructions" for both modes: multi-line, max 500 characters after normalization, a counter, never truncated (Send is blocked above the limit), validated on the server, kept on failure, cleared after a confirmed save |
| FR-NOTE-02 | Notes are stored with the order and appear on the kitchen card, in the owner's active list and in history, after refresh and reconnect |

### 4.3 Orders, timers and numbering

| ID | Requirement |
|---|---|
| FR-ORD-01 | The server accepts an order, validates it, and saves it in PostgreSQL **before** reporting success or broadcasting |
| FR-ORD-02 | Original text is preserved. The only normalization: CRLF/CR → LF, NUL characters removed, leading/trailing whitespace of the whole text trimmed. Internal whitespace and line breaks are unchanged |
| FR-ORD-03 | Maximum text length is 5,000 characters |
| FR-ORD-04 | Statuses are `ACTIVE`, `COMPLETED`, `CANCELLED`. Allowed transitions are only `ACTIVE→COMPLETED` and `ACTIVE→CANCELLED`, enforced on the server |
| FR-ORD-05 | Repeating the same transition is idempotent: completing an already-completed order returns success without changing anything. A conflicting transition returns `409` |
| FR-ORD-06 | `createdAt` and `deadlineAt = createdAt + prepMinutes` are stored in UTC. Timers are derived from `deadlineAt`, never from a browser-only counter |
| FR-ORD-07 | Before the deadline the timer shows remaining `MM:SS`. After it, it counts upward as `+MM:SS` (`+H:MM:SS` once past 1 h) |
| FR-ORD-08 | Timer phases: `normal` (> 5:00 left), `warning` (≤ 5:00 left and deadline not reached), `overdue` (deadline reached or passed) |
| FR-ORD-09 | Timers stay correct across refresh, reconnect and server restart. The client corrects for clock offset using server time |
| FR-ORD-10 | Order numbers are server-generated, sequential per **business day** (Asia/Karachi), unique at the database level, never reused, and safe under concurrent creation and restarts |
| FR-ORD-11 | A business day starts at `BUSINESS_DAY_CUTOFF_HOUR` local time. Default `6` = 06:00 Asia/Karachi (owner decision Q-01: open 17:00–03:00, so an evening shift and its after-midnight orders share one business day and one number sequence) |
| FR-ORD-12 | Display format: zero-padded to at least 3 digits (`001`, `012`, `1000`) |
| FR-ORD-13 | Each order has an immutable internal UUID separate from its number |
| FR-ORD-14 | Every create/complete/cancel is recorded in an audit table with the actor and time |
| FR-ORD-15 | Completed and cancelled orders stay in history until the retention purge (FR-ORD-16). There is no delete endpoint or delete button for any role |
| FR-ORD-16 | Retention (owner decision Q-04): completed and cancelled orders and their audit events are deleted automatically once their business date is more than `ORDER_RETENTION_DAYS` (default `7`) business days before the current one. Active orders are never purged. Daily counters are kept (no customer data), so numbers are never reused. History only offers dates inside the retention window |

### 4.4 Real-time

| ID | Requirement |
|---|---|
| FR-RT-01 | Kitchen and owner screens update without refresh on create/complete/cancel |
| FR-RT-02 | Events are emitted only after the database transaction commits |
| FR-RT-03 | On connect/reconnect, clients load the authoritative snapshot and merge buffered events. Duplicate and out-of-order events are tolerated (version-based) |
| FR-RT-04 | Connection state is always visible: Connected / Reconnecting / Offline |
| FR-RT-05 | Socket connections require a valid session. Logout or revocation disconnects the session's sockets |

### 4.5 Auth and administration

| ID | Requirement |
|---|---|
| FR-AUTH-01 | The first owner account is created with a server-side CLI. There is no web sign-up and no default password |
| FR-AUTH-02 | Passwords are hashed with Argon2id. Minimum length is 12 characters |
| FR-AUTH-03 | Server-side sessions use an httpOnly, Secure, SameSite=Strict cookie. Logout invalidates the session server-side |
| FR-AUTH-04 | Kitchen pairing codes are single-use, expire after 10 minutes, and are stored hashed |
| FR-AUTH-05 | Owners can list and revoke kitchen screens |

## 5. Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-01 | **Reliability:** an order the owner was told is saved is never lost. A WebSocket event is never the only record |
| NFR-02 | **Latency:** target p95 under 1 s from Send to the kitchen card appearing on a healthy connection. Measured by `latency.spec.ts` on the local stack (20 orders, median/p95 reported). It is only re-measured on the real VPS during deployment acceptance |
| NFR-03 | **Security:** see [SECURITY.md](SECURITY.md). Secrets stay out of Git and the frontend; PostgreSQL is never exposed publicly |
| NFR-04 | **Accessibility:** WCAG 2.2 AA contrast and keyboard operability on the owner panel. Kitchen text is readable at 2–3 m |
| NFR-05 | **Browser support:** current Chrome/Edge, Firefox, Safari (owner, incl. mobile). Kitchen: Chromium-based browser on a TV/mini-PC/Android TV box |
| NFR-06 | **Footprint:** runs alongside n8n and Evolution API on a Hostinger KVM 2 (2 vCPU / 8 GB). Target memory caps: db 512 MB, server 384 MB, web 64 MB |
| NFR-07 | **Timezone:** UTC in the database. Asia/Karachi for display and business-day calculation |
| NFR-08 | **Maintainability:** TypeScript strict mode, shared contracts, lint/format/typecheck gates, documented modules |
| NFR-09 | **Testability:** coverage targets in [TESTING.md](TESTING.md) are measured with real tooling |
| NFR-10 | **Privacy:** order text (which may contain customer phone numbers and addresses) is never written to logs |
| NFR-12 | **Installable web app:** web app manifest (name, short name, icons from the logo, `display: standalone`, dark theme colour) so the owner's phone and kitchen tablets can add it to the home screen. No offline order sending: sending always needs the server |
| NFR-11 | **Empty production:** no seed data. Every screen has a meaningful empty state |

## 6. Acceptance criteria (release level)

1. The owner pastes an order, reviews it, presses Send, sees "Order #NNN sent", and the card appears on a paired kitchen screen with a 20:00 or 25:00 countdown. *(E2E)*
2. Refreshing either screen, restarting the server container, or disconnecting the network briefly does not lose orders or reset timers. *(E2E + manual)*
3. Rapid double-clicks and network-timeout retries never create duplicate orders. *(integration + E2E)*
4. Concurrent creates produce unique, gap-free sequential numbers. *(integration)*
5. Completed/cancelled orders leave the kitchen screen only after the server confirms, and they appear in history. *(E2E)*
6. The kitchen session cannot create, complete or cancel orders. Unauthenticated users cannot read orders or connect sockets. *(integration)*
7. A fresh production database contains zero orders and zero users until the owner runs the CLI. *(deployment check)*
8. All quality gates in [TESTING.md](TESTING.md) are PASS, or are explicitly BLOCKED/NOT RUN with a reason.

## 7. Owner decisions (answered 2026-10-29)

| ID | Question | Decision |
|---|---|---|
| Q-01 | Business-day cutoff | Restaurant open 17:00–03:00. Cutoff **06:00** (`BUSINESS_DAY_CUTOFF_HOUR=6`), three hours after closing, so a late close never splits a shift |
| Q-02 | Paste & Send behaviour | **Paste first for review, then click Send** (FR-OWN-05/06) |
| Q-03 | Kitchen "bump" | Left to the developer. Decision: **the kitchen stays read-only**. Only the owner completes or cancels, so a shared kitchen screen cannot close orders by accident and one person stays accountable (ADR-021). Can be added later as a separate change |
| Q-04 | History retention | **Delete after 1 week**: automatic purge, `ORDER_RETENTION_DAYS=7` (FR-ORD-16, ADR-024). Backups are also kept 7 days |
| Q-05 | Domain / hosting | **Online web app on Hostinger** (owner, second answer; Netlify considered and rejected in ADR-026). No domain yet: a domain or subdomain pointing at the VPS is needed before go-live (HTTPS). Building and testing do not wait for it |
| Q-07 | Menu ordering, notes, louder alert (2026-10-30) | **Build them** as additions: a digital menu with + / − next to Paste / Type, kitchen notes on every order, and a 3–4 s alert with volume and test settings (ADR-027, ADR-028). Not a POS: no billing or payments |
| Q-08 | More preparation targets (2026-10-30) | **Add 15 and 30 min** next to 20 and 25. 20 stays the default |
| Q-06 | Logo | **Take it from the menu.** Menu images are now in `docs/assets/brand-reference/`. The logo (red triangle, "91°", "Degree" script, wing, "B.B.Q. \| FAST FOOD \| CHINESE") is cropped from them **without redesigning it** |
