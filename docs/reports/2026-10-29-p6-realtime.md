# Report — P6 Realtime (Socket.IO)
Date: 2026-10-29 (Asia/Karachi) · Phase/step: Phase 2, P6 · Author: Claude Code

## 1. Summary
Live updates work and only go one way, from server to screens:
- **Connection:** Socket.IO 4.8.4 with its default transports (polling handshake, then a WebSocket upgrade).
- **Handshake:**
  - The session cookie is required.
  - A foreign Origin is rejected; a missing Origin is allowed (ADR-023).
  - Each connection joins the `orders` room and a room for its own session, then receives `server:hello { serverTime, role }`.
- **Order events:** `order:created` and `order:updated` are broadcast from the in-process `OrderEventBus`, which the orders service publishes to only after the database commits.
- **Revocation:** logout and device revocation emit `session:revoked` and then disconnect that session's sockets.
- **Sweeper:** every 60 seconds it re-checks connected sessions and disconnects any that expired, idled out or belong to a disabled owner (e.g. disabled from the CLI).
- **Client messages:** anything a client emits is ignored.
- **Shutdown:** graceful shutdown now closes Socket.IO, which also closes the HTTP server.

What the tests prove:
- **Handshake:**
  - Rejected: no cookie, a forged cookie, a logged-out cookie, and a foreign Origin (even with a valid cookie).
  - Accepted: a missing Origin with a valid cookie.
  - A polling-only client connects.
  - Both roles receive `server:hello`.
- **Revocation and sweeper:**
  - Logout leads to `session:revoked LOGOUT` and a server disconnect.
  - Revoking one kitchen device disconnects only that screen.
  - The sweeper disconnects an idled-out session and a disabled owner, and leaves live sessions connected.
- **Order events:**
  - `order:created` reaches the kitchen and owner screens and passes the shared schema.
  - Nothing is emitted for an idempotent replay or a rolled-back create.
  - `order:updated` is emitted once for a completion and not for a repeat.
  - Events emitted by a client are ignored and change nothing.
